Inference with Reference, step by step

When most of an answer already exists in the prompt, the model doesn't need to write it one token at a time. The decoder copies a guess from the reference, the model checks the whole guess in a single forward pass, and every token it agrees with is kept. The output is exactly what normal decoding would produce. Only the number of passes changes.

  1. Look upTake the last 2–4 generated tokens and search for them in the reference text.
  2. DraftIf found, copy up to 8 tokens that came next in the reference as a guess.
  3. VerifyOne forward pass scores all drafted tokens at once against what the model would write.
  4. AcceptKeep the longest prefix that matches, plus the model's own next token. Throw away the rest.

What it saves

Sequential forward passes, so latency and GPU time per request. With a whole-document edit, almost everything outside the selection is copied in long accepted runs.

What it doesn't save

Output tokens. The model still emits every token of the document. If the app only needs the selection, asking for the selection alone and splicing it in code is cheaper still.

Why the output is identical

A drafted token is kept only if it equals what the model would have chosen itself at that position. Wrong guesses cost a little extra compute in that pass and nothing else.

Where it stops helping

New text, like the rewritten paragraph, rarely matches the reference, so those tokens come one per pass. The simulation uses words as tokens; real tokenizers split finer, which usually makes runs longer.

The model we serve

Meet Ministral 3 8B Instruct

mistralai/Ministral-3-8B-Instruct-2512 is the middle size of Mistral's Ministral 3 family, released on 2 December 2025 under Apache 2.0. The family comes in 3B, 8B and 14B, each as Base, Instruct and Reasoning, and every variant can read images.

The models were not trained from scratch. Mistral calls the method cascade distillation: start from Mistral Small 3.1 (24B), prune it to 14B and distill, then prune 14B to 8B, then 8B to 3B. Each step trained on 1–3 trillion tokens, much less than a from-scratch run.

Tekken tokenizer

A byte-level BPE in the style of OpenAI's tiktoken, with 131K entries. A large vocabulary means common words, including many non-English ones, become single tokens, so a document is fewer tokens long.

Mistral lists English, French, Spanish, German, Italian, Portuguese, Dutch, Chinese, Japanese, Korean and Arabic, and says dozens more work. Turkish is not mentioned anywhere, so we should test it ourselves.

FP8 weights

The official checkpoint is already 8-bit floating point (E4M3). Each weight matrix has one scale for its weights and one fixed scale for its inputs, so matrix multiplies run on the GPU's FP8 units.

Embeddings, output head and vision tower stay in BF16. The weights are about 10.4 GB, which Mistral says fits in 12 GB of VRAM.

Why n-gram drafting fits

Mistral publishes no draft model, EAGLE head or multi-token prediction layers for Ministral 3. N-gram lookup needs none of those, because the document itself is the draft source.

The tokenizer matters here: the lookup matches token sequences, so the same text must tokenize the same way in the prompt and in the output. Byte-level BPE makes that the normal case.

GPU memory on our card

We give vLLM 30% of the 96 GB card, about 29 GB. The KV cache stores keys and values for every token in flight:

per token = 2 (K,V) × 34 layers × 8 KV heads × 128 dims × 2 bytes = 139,264 B ≈ 136 KiB 32K tokens = 139,264 × 32,768 ≈ 4.56 GB
Weights 10.4 GB KV cache ≈ 16 GB, room for about 3.5 full 32K documents at once Activations and CUDA graphs ≈ 2.4 GB (estimate)

Serving tips

Mistral's recommended vLLM flags are --tokenizer_mode mistral --config_format mistral --load_format mistral, which load its own tokenizer library and the single consolidated.safetensors file. We currently load the Hugging Face format, which also works. For production Mistral suggests temperature below 0.1; for edits we use 0, which also gives speculation the highest acceptance.
